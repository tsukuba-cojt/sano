## 1. 識別子

| 名前 | 値 |
|---|---|
| Service UUID | `6b616972-616e-4b41-4952-414e00000010` |
| RX Characteristic（central → peripheral、Write Without Response、Write 可） | `6b616972-616e-4b41-4952-414e00000011` |
| TX Characteristic（peripheral → central、Notify） | `6b616972-616e-4b41-4952-414e00000012` |
| エポック（created_at / expires_at の起点） | 2026-01-01T00:00:00Z = Unix 1767225600 |
| プロトコルバージョン | 1（当面 1 のまま送る。受信側は不一致でも切らない。能力は HELLO の caps で伝える）（v2: C13） |

- 広告には **Service UUID のみ** を載せる（Local Name なし、Manufacturer Data なし）。iOS はバックグラウンドで UUID が overflow area に移るため、Android スキャナは Apple 製造者データ（Company ID 0x004C、先頭バイト 0x01）も候補として扱い、接続後にサービス探索で確認する。
- 全 characteristic / 接続は平文（暗号化・ペアリング要求なし）。
- ノード ID: 端末ごとに生成した 8 バイト乱数（永続）。

## 2. メッセージ封筒（Envelope）

```
offset size  field
0      1     magic      = 0x4B ('K')
1      1     version    = 1
2      1     kind       0=notice(お知らせ) 1=group_info(グループ情報) 2=tombstone(取り消し)
                        3=help(困りごと) 4=ack(受け取りました)                       （v2: C21）
3      1     flags      bit0: body が deflate+辞書 で圧縮されている
                        bit1: supersedes フィールドあり
                        bit2-7: 予約 (0)。訓練は見出しの接頭辞「【訓練】」で表し flags は使わない （v2: C23）
4      3     group_id   uint24, 0..999999（6 桁の参加コードと同じ数）
7      8     msg_id     uint64 = SHA-256(group_id(3) ‖ kind(1) ‖ origin_id(8) ‖ created_at(4)
                        ‖ body_plain ‖ [supersedes(8 LE)]) の先頭 8 バイト。supersedes は あるときだけ含める （v2）
15     4     created_at uint32, エポックからの秒
19     4     expires_at uint32, エポックからの秒。中継時に残り時間へ書き換える（§2.3）   （v2: C12）
23     1     hop        中継回数。発信時 0。受信側は保存時に +1。64 以上は中継しない
24     1     category   後述
25     1     role       0=住民 1=スタッフ 2=公式（発信者）
26     2     body_len   uint16, 送信される body（圧縮後）のバイト長
28     [8]   supersedes flags bit1 が立っているときのみ。上書き/取消対象の msg_id
..     body_len  body
```

- ヘッダは 28 バイト（supersedes ありで 36）。**offset 0〜27 の位置と意味は将来の版でも変えない**（旧版が新版の封筒をヘッダだけで中継できるように。§2.1）。（v2: C13）
- **msg_id は hop を含まない**（hop は中継ごとに変わる）。role / category も含まないが、受信側はこれらを「最初に受け取った値」で固定する。expires_at も含まないため、中継時の書き換え（§2.3）は msg_id に影響しない。supersedes は（あれば）含める。同じ端末が同じ秒に複数の取り消し・書きなおしを出しても ID が衝突しないようにするため。origin_id はワイヤに載らないので受信側は msg_id を再計算しない（v1 と互換）。（v2: C12, C13）
- `kind=notice` の body（平文）は `u16 len + UTF-8` のフィールドを順に連結:
  1. sender_name（発信元表示名、≤ 48 バイト）
  2. title（見出し、≤ 120 バイト）
  3. place（場所、≤ 120 バイト）
  4. text（本文、≤ 3,000 バイト）
  5. ext（省略可、≤ 64 バイト）: `flags u8`。bit0 = **返事を 求める（安否確認）**。立っていると受信側の詳細に「無事です」「家に います」「困っています」「助けて」の返事ボタンを出す。公式・スタッフ（role ≥ 1）の notice だけに付ける。書きなおしは元の印を引き継ぐ。（v2.1: C21 拡張）
  5 番目が壊れていれば ext なしとして読み、6 番目以降のフィールドは無視する（旧版・新版の相互運用のため末尾の余りを拒否しない）。（v2: C13, C25）
- `kind=help`（住民からの知らせ）の body は notice と同形式で、5 番目の ext に種類などを載せる（`lib/core/report.dart`）。（v2: C21、v2.1 で SOS・安否・在宅避難に拡張）
  - ext: `type u8 ‖ people u8 ‖ needs u8 ‖ flags u8 ‖ in_reply_to i64 LE（省略可）`。type: 0 = SOS（助けて）、1 = 無事です、2 = 家に います（在宅避難）、3 = 困っています（未知の値は 3 として読む）。people: 人数（0 = 書いていない、5 = 5人以上）。needs: bit0 水・食べ物が ない、bit1 薬・医療が 必要、bit2 動けない・助けが 必要、bit3 トイレが 使えない、bit4 電気・ガスが 止まっている、bit5 その他（未知のビットは無視）。flags bit0 = けがを している 人が いる。in_reply_to: 返事先の安否確認 notice の msg_id（0 = なし）。ext が 4 バイト未満なら種類不明として見出しだけ表示、12 バイト以上なら返事先あり、余りは無視。
  - title は端末が自動で作る（例「【SOS】助けが 必要です（2人）」「【無事】山田 花子 さんは 無事です（3人）」「【在宅避難】家に います（3人） ・ 水・食べ物が ない ほか」「【困りごと】薬・医療が 必要（2人）」）。sender_name は無事です・在宅避難のときだけ任意の名前（SOS・困りごとは空）。place は町名と目印（番地は書かせない）、text は 40 文字までのひとこと。
  - category=14 支援要請、role は送った端末の役割（住民は 0）。有効期間: SOS 24 時間、困りごと 2 日、無事です・在宅避難 3 日。同じグループ・同じ種類は 30 分（SOS は 10 分）たつまで端末側で送り直させない。
  - 送れるのは、グループ情報の policy bit2（住民からの 知らせを 受け付ける）が立つグループ、または返事を 求める notice への返事（in_reply_to が同じグループの期限内の安否確認）のとき。
  - 表示するのはそのグループの公式・スタッフ端末だけで、住民端末は保存・中継のみ（表示上の分離であり秘匿ではない）。送った本人は「送った 知らせ」で状態を見て、取り消せる（tombstone。中継端末では本文を消して空殻にする）。
- `kind=ack` の body は空。supersedes 必須（対象の help の msg_id）。公式・スタッフ端末が「受け取りました と 返す」で出す（role はその端末の役割）。有効期間は min(対象の期限 + 24 時間, 発信から 72 時間)。「置き換え」扱いにはしない（対象は表示されたままで、詳細に「〇〇市 防災課が 受け取りました（午後3時10分）」を示す）。対応の約束ではない。（v2: C21）
- 返信の検索（`ackFor`）は role がスタッフ・公式のものだけを採用し、対象が保存済みなら group_id も一致させる。住民の ack や別グループの ack で未確認 SOS の保護を解除しない。role の検査は電子署名による発信者認証ではない。（v2.4）
- `kind=group_info` の body（平文）: 同形式で 1. name（グループ名 ≤ 60 B）2. host_name（≤ 48 B）3. policy（1 バイト: bit0 = 参加者も投稿可、bit1 = 閉鎖（引っ越し済み）、bit2 = 困りごとを受け付ける）4. description（問い合わせ先・ひとこと ≤ 300 B）5. ext（省略可）: `u16 len ‖ code_digest 8 B ‖ generation u16 ‖ successor uint24`。code_digest = SHA-256(本部コード 8 桁 ASCII) 先頭 4 B ‖ SHA-256(スタッフコード 8 桁 ASCII) 先頭 4 B（全 0 は「なし」）。generation はコードの作り直し・引っ越しごとに +1。successor は後継の参加コード（0 = なし。999999 超は 0 扱い）。ext が 13 バイト未満なら ext なしとして読み、6 番目以降のフィールドは無視する。group_info は role=2 で発信され、expires_at は作成から 365 日。（v2: C24, C21）
- `kind=tombstone` の body は空。supersedes 必須。受信側は対象 msg_id を「取り消し済み」として表示から外し、他人の notice は本文を消して空殻にする（§5）。（v2: C20）
- 圧縮: `flags bit0` が立つ場合、body は **raw deflate（zlib ヘッダなし、windowBits=-15）+ 事前共有辞書**（`lib/core/dictionary.dart` の `kDictionaryV1`、UTF-8 バイト列）。伸長後サイズは **4,096 バイト上限**（超過は破棄）。圧縮しても縮まない場合は圧縮しない。

### 2.1 受信側の検証（2 段）（v2: C13）

| 段 | 条件 | 満たさないとき |
|---|---|---|
| 中継できる条件 | magic 一致、ヘッダ 28 B 以上（flags bit1 なら supersedes 8 B も揃っている）、body_len と実長の一致、body_len ≤ 4,096、expires_at ≥ created_at、group_id ≤ 999999。保存時はさらに hop < 64 と有効期間が §2.3 の範囲内 | 破棄（セッションは続ける） |
| 表示できる条件 | version = 1、既知の kind、予約 flags = 0、既知の role、伸長成功（flags bit0 のとき body_len > 0 かつ伸長後 ≤ 4,096）、body の形式（フィールド長・UTF-8。tombstone / ack は supersedes 必須で body 空） | **不透明メッセージ**として扱う |

- 不透明メッセージ: 生バイトのまま保存し、目録（INVENTORY）に載せ、中継する。表示も伸長もしない。hop は offset 23、expires_at は offset 19 を直接書き換える。期限・削除順はヘッダだけで判定する。端末内 **300 件かつ保存上限の 10%** まで（超えたら受信の古い順に捨てる）、1 セッション **16 KB** まで、HELLO caps bit0（未知版中継可）を立てた相手にだけ送る。（v2: C13）
- 旧版（v1）の端末は不透明メッセージを捨てる。旧版が中継できるのは version=1・既知 kind・予約 flags=0 の封筒だけなので、v2 の拡張（help / ack・group_info の ext・notice の 5 番目）はこの範囲に収めている。（v2: C13）

### 2.3 有効期限（相対期限）（v2: C12）

- 受信側は expires_at を自分の時計と比べない。**local_expiry = 受信時刻 + (expires_at − created_at)** を正とする（自端末発信は expires_at そのまま）。「created_at が未来なら破棄」も入れない（進んだ時計も同じ頻度で起きる）。
- 受信時に破棄するのは、有効期間 (expires_at − created_at) が 0 以下、または上限を超えるときだけ: notice / help は 30 日超、tombstone / ack は 31 日超（対象の 30 日 + 猶予 24 時間）、group_info と不透明メッセージは 366 日超。
- 中継時は **expires_at := created_at + (local_expiry − now)** に書き換えて送る（msg_id は expires_at を含まないので合法）。残り時間は縮む一方なので「中継ごとに延びる」は起きず、総寿命は元の有効期間を超えない。v1 端末は短くなった絶対 expires_at を見るだけなので相互運用する。
- hop: 発信時 0。受信側は保存時に +1（255 で頭打ち）。64 以上は保存も中継もしない。

## 3. リンク上のフレーム

リンク（1 本の GATT 接続）は**双方向のバイトストリーム**として扱う。central → peripheral は RX への Write Without Response、peripheral → central は TX の Notify。1 回の書き込み/通知は `maxChunk` バイト以下（ATT MTU − 3、ただし **512 バイトまで**。Android の GATT は属性値を 512 バイトまでしか扱わず、514 バイトの書き込みは失敗し続けるため）。フレームはチャンク境界と無関係に連結される。送る側は続けて送るフレームを詰めて、1 回の書き込みを `maxChunk` いっぱいに使ってよい（お知らせ 1 件 約 160 バイトを 1 回ずつ書くと遅い）。受ける側は購読の完了より先に届いた通知・書き込みを捨てずに溜め、リンク確立の直後に渡す（相手は購読を受けた直後に HELLO を送るため）。（v2.4）

```
frame = u16 length (type + payload の長さ) ‖ u8 type ‖ payload
```

| type | 名前 | payload |
|---|---|---|
| 0x01 | HELLO | version(1) ‖ node_id(8) ‖ store_count(u16) ‖ caps(1) ‖ [count(u8) ‖ group_id(uint24) × count]（末尾は caps bit2 のときだけ。最大 8 件。受信側は読めない余分を無視する）（v2: C13, C17） |
| 0x02 | INVENTORY | count(u16) ‖ msg_id × count（8 バイトずつ）。複数回送ってよい（1 フレーム 1,023 件まで） |
| 0x03 | INVENTORY_END | なし |
| 0x04 | TIME | u32 現在エポック秒。HELLO 直後に送る。受信側は「相手の時計 − 自分の時計」を記録する（v2: C12） |
| 0x05 | INVENTORY_CUTOFF | u32 目録に含めた中で最古の created_at。目録を絞ったときだけ INVENTORY_END の直前に送る。受信側はそれより古い notice / help を送らない（v2: C08） |
| 0x06 | INVENTORY_FILTER | 目録の要約（Bloom フィルタ）: `salt u32 LE ‖ hash_count u8 ‖ item_count u32 LE ‖ bits`。双方が caps bit4 を立てたときだけ、INVENTORY の代わりに 1 つ送る。1 件あたり約 9.6 ビット（3,000 件で約 3.6 KB、一覧の約 1/7）、偽陽性 約 1%。ビットの位置は splitmix64(msg_id ^ salt) を元にした二重ハッシュで決め、salt はセッションごとに変える（誤って送られなかったものは次のすれ違いで送られる）。偽陰性はない（v2.3） |
| 0x10 | MESSAGE | 封筒 1 件（§2 のバイト列そのまま） |
| 0x11 | MESSAGES_END | なし、または u8 flags（この方向の送信完了）。bit0 = 送信上限で打ち切った（続きがある）、bit1 = こちらから接続できないので短い間隔で同期しに来てほしい（peripheral 側だけ）。旧版は payload を読まない（v2.2） |
| 0x12 | STORED | flags(u8) ‖ count(u16 LE) ‖ msg_id(i64 LE) × count。1 フレーム最大 1,023 ID。flags bit0=最後（count=0）。双方が caps bit5 を持つ場合のみ使用。受信して永続保存した ID の確認（v2.4） |
| 0x20 | BYE | なし |

不明な type は payload を読み飛ばす（状態判定より前に捨てるので、HELLO より前に届いても切らない）。length が 8,192 を超える、または 0 のフレームは不正としてリンクを切る。

### HELLO の caps（v2: C13）

| bit | 意味 | 立てる端末 |
|---|---|---|
| bit0 | 未知の version / kind / flags の封筒（不透明メッセージ）を中継できる | 全端末（C13） |
| bit1 | 中継役（設定「中継役として 使う」オン） | 中継役（C04, C17） |
| bit2 | HELLO 末尾に参加グループ一覧あり | 中継役だけ（私物端末は所属グループを露出しない）（C17） |
| bit3 | HELLO 直後の先出し（PUSH）を受けられる | 全端末（C08） |
| bit4 | 目録を要約（INVENTORY_FILTER）で送受できる | 全端末（v2.3） |
| bit5 | 受信情報の永続保存を STORED で確認できる | 全端末（v2.4） |
| bit6〜7 | 予約（0） | — |

- HELLO の version は当面 1 のまま送る。受信側は不一致でもログに残すだけで切らない。（v2: C13）

## 4. 同期セッション

リンクが開いたら両側が対称に以下を行う（central/peripheral の区別なし）。

1. HELLO を送り、続けて TIME を送る。（v2: C12）
2. **先出し**（docs/08 の「手順 1.5」。相手の HELLO を受けた時点で行い、手順 3 の目録はその後に送る）: 相手の HELLO を受け取り caps bit3 が立っていれば、相手の INVENTORY_END を待たずに、次の順（各 created_at の新しい順）で合計 **16 件・8 KB** まで MESSAGE で先に送る。① SOS（どのグループでも、24 時間以内、まだ ack が無いもの。中継中のほかの人の SOS を含む）② 公式・スタッフの避難情報と注意喚起（どのグループでも、24 時間以内、訓練を除く）③ 参加グループの tombstone（24 時間以内）④ 参加グループの最新 group_info ⑤ 自分が出した help（24 時間以内・ack なし）⑥ 参加グループの ack（24 時間以内）⑦ 参加グループの公式 notice（24 時間以内）。取り消し・置き換え済みと、前回のすれ違いで相手が持っていると分かったもの（途中で切れたセッションの分も含む）は除く。先出し分はセッション上限（手順 4）に含め、後段の送信から除外する。受信側は msg_id 既知なら無視する。**MESSAGE は相手の INVENTORY 受信中にも届いてよい**（MESSAGES_END の後だけ不正）。（v2: C08、v2.3 で SOS と避難情報を最初に）
3. 相手の HELLO を受け取って先出しを送ったあと、自分が持つ有効な（期限内・hop<64）メッセージの msg_id を目録として送り、INVENTORY_END を送る。空殻（§5）・書きなおされた古い版・古い group_info も載せる（送り返されないように）。**双方が caps bit4 を立てていれば INVENTORY_FILTER（要約）を 1 つ**、そうでなければ msg_id の一覧を新しい順に最大 **3,000 件**、INVENTORY で送る。一覧で送るとき `maxChunk` が **100 バイト未満**なら受信時刻の新しい順 **300 件**に絞り、INVENTORY_END の直前に INVENTORY_CUTOFF（含めた中で最古の created_at）を送る。相手はそれより古い notice / help を送らない。（v2: C08、v2.3 で要約）
4. 相手の INVENTORY_END を受け取ったら、「自分にあって相手にない」（一覧に無い、または要約で「持っていない」と判定された）msg_id を優先順に並べ、MESSAGE で送る。優先順は **送る順の段 → 相手の参加グループに属するもの（相手が HELLO に一覧を載せたときだけ）→ role 降順 → created_at 降順**。段は 0: SOS（ack なし）・公式とスタッフの避難情報と注意喚起、1: tombstone・ack・group_info、2: そのほかの help（ack なし）、3: 公式とスタッフの重要なお知らせ（避難所・給水・炊き出し・物資・医療）、4: そのほかの公式とスタッフのお知らせ・ack 済みの help、5: 住民のお知らせ・不透明メッセージ、6: 訓練（見出しが【訓練】）。書きなおされた古い版（supersededBy あり）と、同じグループのもっと新しい group_info がある古い版は送らない。送信バイト合計が **セッション上限（既定 65,536 バイト）** に達したら打ち切る（MESSAGES_END bit0）。不透明メッセージは相手が caps bit0 のときだけ、1 セッション 16 KB まで（超えた分は飛ばして次へ）。送るときは expires_at を残り時間に書き換える（§2.3）。最後に MESSAGES_END。（v2: C17, C13, C12、v2.3 で送る順の段）
5. 受信した MESSAGE は検証し、保存待ちに入れる（hop+1、受信時刻記録）。最大 128 件ずつ保存し、保存成功後に一覧・通知・目録へ公開する。重複（msg_id 既知）は再保存しない。中継できない封筒は捨てる。保存例外は交換を失敗として終了する（v2.4）。
6. 自分が MESSAGES_END を送り終え、かつ相手の MESSAGES_END を受け取ったら、自分の受信保存が終わるまで待つ。**双方が caps bit5 に対応**していれば、保存した受信 ID を STORED で送り、最後に count=0・flags bit0=1 を送る。相手からの最終確認まで待ち、双方の保存確認が揃ってから、**接続を開始した側（central）** が BYE を送ってリンクを閉じる。確認 ID は今回送信した ID の部分集合でなければ不正。保存確認前の切断・タイムアウトを正常終了にしない。旧版相手は従来どおり BYE／closing 中の切断で終了できるが、保存確認のない送信を「渡した台数」へ加算しない（v2.4）。
7. タイムアウト: HELLO 待ち 5 秒、全体 30 秒。超過したらリンクを閉じる。失敗終了時の BYE は送信完了を待たず、応答しない送信で接続枠の解放を止めない。

次回の先出しで除外する「相手が持っていると分かったもの」は、相手の正確な一覧目録・保存確認・相手から受け取った ID に限る。Bloom 要約の陽性には誤判定があるため、次回の先出し抑制へ持ち越さない（[1 万件の負荷確認と改善](12_capacity_measurements.md)）。

### 受信の上限（v2.4）

- 保存待ちは **1 接続 2,048 件かつ 4 MiB、端末全体 4,096 件かつ 8 MiB**。バイト数は封筒サイズ＋展開本文サイズ＋1 件 128 B で数える。保存済み・破棄分の予約を解放する。
- MESSAGE の受信量は通常 **64 KiB**、中継役どうし **1 MiB**。相手と MTU が異なる可能性があるため、小 MTU の送信上限 256 KiB を受信側には適用しない。
- それ以外の制御フレームは合計 **64 KiB**、一覧形式の INVENTORY は **3,000 ID** まで。
- 上限超過・保存失敗はその接続を失敗として終了する。未保存分を保存済みと通知しない。次の交換では保存済みの目録との差分から再開する。

### 中継役どうしの交換（v2: C17）
- 両方の HELLO で caps bit1 が立っていれば、転送開始前にセッション上限を **1 MB**（`maxChunk` が 180 バイト未満なら **256 KB**）、全体タイムアウトを **300 秒**に差し替える。片方だけ・どちらも立っていなければ通常のまま（中間段は置かない）。
- 先出し（手順 2）の 16 件・8 KB は中継役どうしでも同じ。

### セッションの重複と再接続抑制
- HELLO の node_id が既に進行中のセッションと同じなら、ノード ID が小さい側が開始したリンクを残し、もう一方に BYE を送って閉じる。自分自身の node_id なら閉じて 15 分無視する。
- 同じ node_id との再接続は **60 秒** 空ける。ただし前回の同期の後に、相手がまだ持っていない中継できるメッセージ（相手の目録 ∪ 渡したもの ∪ 受け取ったもの に無いもの）が入ったときは待たずに再接続する。中継役どうし（自分が中継役で、前回の同期で相手も中継役だった）は **10 秒**。（v2: C17、v2.2 で判定を正確に）
- **続きの同期**（v2.2）: どちらかが MESSAGES_END の bit0（打ち切り）を立てたら、**2 秒**後に続きを同期する。maxChunk が 100 未満のリンクでは 1 回の上限を maxChunk × 256 バイト（最小 4 KB）に下げ、30 秒以内に終えて続きで送る。
- **受信リンクでしか会えない相手**（v2.2）: peripheral 側は、HELLO の node_id の端末を広告で見つけていない（自分から接続できない）とき MESSAGES_END の bit1 を立てる。central 側はその相手と **20 秒** 間隔で同期し直す。
- **再接続の見直し**（v2.2）: 15 秒ごと、およびセッションが終わるたびに、近くの端末（広告で見つけた相手のうち、60 秒以内に見えた相手、または 1 度同期できて 2 × 再接続間隔 + 15 秒以内に見えた相手）を「まだ同期していない → 最後の同期が古い → 電波が強い」の順に見直し、枠が空いていれば接続する。発見の通知が繰り返し来ない環境（iOS の背面）でも、近くに居続ける相手と同期し続け、受け取ったものをすぐ別の相手へ渡し、上限で後回しにした相手とも同期するため。離れた相手には数回失敗するだけで止まる。
- 接続失敗した peerId は 30 秒バックオフ。直前に成功した相手でも、その後に開始した同期の保存上限エラーなどは同じく待つ。別のリンクが同期中、またはこのリンクの開始後に別の同期が成功した場合は、重複リンクとして失敗を加算しない。Apple 製造者データ由来の候補でサービスが見つからなかった peerId は 15 分無視する。
- 同時接続: central として最大 2（中継役は 3）、peripheral として最大 4。（v2: C04）

## 5. 保存と中継の方針

- **v2.4: SOS の保護**。期限内・未取消・通常形式（不透明・空殻を除く）の help で、ReportType が SOS、対応する ack がないものは、参加グループや役割によらず容量削除の対象から外す。新しい SOS の受信でも保護中の SOS を押し出さない。削除候補がなければ保存上限のエラーを返す。ack 済み・期限切れ・取消済みは通常の削除順へ戻す。全枠が SOS でも、その SOS を対象にした同一グループのスタッフ・公式 ack の追加では、対象だけを同じトランザクション内で削除候補にできる（返信を保存できない詰まりを避ける）。
- **v2.4: 本部記録**。`reports.bin` に本部・スタッフの受信報告と最新返信を別保存する。30 日・10,000 報告・64 MiB の上限と表示条件は [11 §2](11_bulk_data_reliability.md#2-保存領域を役割で分ける)。この保管によって中継 TTL は延長しない。
- **v2.4: 保存の確定**。追加・一括追加・既読・期限掃除・削除は判定を含め直列化する。作業用の状態を準備してから書き込み、成功後だけ公開する。失敗時は公開済みの状態を保ち、後続の書き込み前にその状態でファイルを修復する。削除を伴う追加は削除数にかかわらず全記録を `rewrite` し、`FileStoreBackend` の一時ファイル書き込み・置換で確定する。削除だけが記録された時点で終了して新着も失うことを防ぐ。削除のない追加は追記・一括追記を使う。本部記録の本文消去も即座に `rewrite` し、追記ログの旧本文を残さない。
- 保存上限 3,000 件。満杯になったら **10%（300 件）をまとめて削除**する。上記の SOS 保護を適用したうえで、削除順は **期限切れ → 不透明メッセージ・書きなおされた古い版・古い group_info → 未参加グループ（住民 → スタッフ → 公式、各受信の古い順）→ 参加グループ（同順）→ 自端末発信**。古い版は消すまで保存して目録に載せ、相手から同じものを受け取り直さない。利用者が手で消す操作は置かない（消すと目録から外れ、すれ違うたびに同じものを受け取り直して短いすれ違いを無駄にするうえ、ほかの人に要るものまで失うため）。（v2: C08, C13, C17、v2.3 で古い版）
- 不透明メッセージは別枠で 300 件かつ保存上限の 10% まで。超えたら受信の最も古い不透明メッセージを 1 件捨ててから保存する。（v2: C13）
- 1 グループあたり住民（role=0）の notice は端末内 **500 件**まで。超えたら受信の最も古いものを 1 件捨ててから保存する（自端末発信は数えない。住民投稿は届かない・消えることがある）。（v2: C08）
- 参加していないグループのメッセージも保存・中継する（表示しない）。
- tombstone は対象より長く（対象の local_expiry + 24 時間）保持する。supersedes 付き notice も同じく対象の local_expiry + 24 時間まで保持し、自身の期限後は表示しないが目録・中継には使う（先に消えた端末で旧版が復活するのを防ぐ）。保持期限は対象を見たときに決まり、対象が先に消えても有効。（v2: C01）
- **tombstone / supersedes の適用は、同じ group_id で、封筒の role が対象の role 以上のときだけ**（住民は公式を消せない）。supersedes は対象が notice のときだけ適用し、複数あれば created_at が最新のものを「置き換え済み」の先とする。ack は置き換えにしない。適用されないものも保存・中継はする。（v2: C10, C21）
- 取り消された**他人の** notice は本文（sender_name・title・place・text）を端末から消し、ヘッダ（msg_id・group_id・kind・flags・category・role・created_at・expires_at・hop・supersedes）だけの**空殻**にする。空殻は目録には載せる（再受信を防ぐ）が MESSAGE では送らない。発信者本人の端末と、そのグループの公式端末（ホスト・本部コードで昇格）では本文を残す（再投稿で復旧できるように）。公式（role=2）の tombstone が住民・スタッフの投稿を取り消したときは「公式による取り消し」として記録する。（v2: C20, C10）
- group_info は同じ group_id の中で **世代（generation）→ created_at** の順で新しいものを採用する（時計のずれで古い方が勝つのを防ぐ）。（v2: C24）
- 未参加グループの group_info は「近くで 流れている グループ」用に、最後に受け取った時刻の新しい順に最大 3 件を列挙できる。（v2: C22）
