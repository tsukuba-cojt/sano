# 本部記録 1 万件の負荷確認と改善

実施日: 2026-11-13

本部の記録を上限の **10,000 件** まで増やし、受信、一覧の集計、一括返信、再起動後の復元を確認した。保存した全報告と返信を復元でき、10,001 件目は既存の記録を消さずに保存エラーとなる。CI は使わず、ローカルで再実行できる計測コードと結果を残す。

保存期間・上限・保存成功の定義は [大量受信時の仕様](11_bulk_data_reliability.md) に従う。

スマートフォン間の通信時間、歩行中に渡せる件数の試算、画面を消したときの条件は [BLE の通信時間と歩行中の試算](13_ble_encounter_estimates.md) に分けて記録する。

## 1. 今回直したこと

| 問題 | 変更 |
|---|---|
| 新規受信も 500 件ごとに本部記録の全ファイルを書き直していた | 新規受信は追記する。古い更新ログが増えたときだけ全体を整理する |
| 返信 1 件のたびに全記録のコピー、容量計算、返信索引の作成を繰り返した | 変更分だけを準備し、保存成功後に容量・返信索引へ反映する |
| 起動時に全記録を読み、再び全件を符号化していた | 最新の保存バイトを再利用し、256 レコードごとに画面や入力の処理へ戻る |
| 通信状態の変化だけでも一覧・SOS の集計をやり直していた | 本文解析と一覧・集計を再利用する。データ・閲覧権限・期限・時計の巻き戻りを反映して作り直す |
| 一括返信の進み具合が見えず、中継の保存枠から外れた返信も完了と見えた | 保存件数の進捗と準備待ち件数を表示し、準備待ちも再試行の対象に残す |
| 30 日を過ぎた本部記録が、中継ファイルの掃除前だけ履歴や詳細に再表示された | 中継側から表示する場合も本部記録の 30 日を適用する |
| 相手の目録要約の誤判定を、次の接触でも「相手が持っている」と扱った | 次回の SOS 先出しを止める根拠は、正確な一覧・受信・保存確認に限る |
| 保存先が満杯になった直後、接続をやり直し続ける場合があった | 独立した同期の失敗は、直前の成功にかかわらず 30 秒待って再試行する |
| 接続を終了する BYE の送信待ちで、タイムアウト後も接続枠が残った | 失敗した接続は BYE の送信完了を待たずに閉じる |

本部記録のログ整理は、現存レコードの合計サイズの 1/4 を目安にする。余分なログの許容幅は最小 256 KiB、最大 4 MiB。削除・取り消しによる本文消去・書き込み失敗からの修復では、引き続きその場でファイルを全置換する。再起動時もログの実際のサイズから整理の要否を判断する。

## 2. 計測方法

- Mac / arm64、macOS 26.5、Flutter 3.44.4、Dart 3.12.2。
- `flutter test` 上で `FileStoreBackend` を使い、一時ディレクトリへ実際に書き込む。通信は `FakeRadio`、グループ設定はメモリ内で保持する。
- 1,000 件を測った後、別の一時ディレクトリで 10,000 件を測る。報告の種類は SOS 1%、残りは無事・在宅避難・困りごと。本文には乱数シード固定の 120 文字を含める。
- 受信は 128 件ずつ、一括返信はアプリと同じ 100 件ずつ。再起動は同じデータファイルから新しい `AppController` を作る。
- 一覧・人数集計・SOS 件数をまとめて 21 回呼び、中央値と 95 パーセンタイルを出す。最初に一覧を作る時間も別に記録する。
- 10 ms 間隔のタイマーが実行される間隔から、処理中にイベントを長く止めていないかを確認する。これは実画面のフレーム時間ではない。
- メモリ値は Flutter テストプロセス全体の RSS。VM・JIT・テスト環境・直前のケースも含み、スマートフォン上のアプリ単体の使用量ではない。

変更前は `cb7b79d`、変更後は本仕様書と同じ変更一式で測る。同じ計測コードを両方に使う。数値はこの Mac での参考値で、BLE の転送時間や低性能端末での速度を保証するものではない。

## 3. 計測結果

10,000 件での結果。時間は四捨五入、MB は 1,000,000 バイト。書き込み量は本部記録ファイルへの累計で、中継用ファイルは含まない。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 受信・保存 | 484 ms | 469 ms |
| 最初の一覧作成 | 6.9 ms | 13.2 ms |
| 繰り返しの一覧・集計・SOS 件数（中央値） | 15.01 ms | 0.35 ms |
| 同 95 パーセンタイル | 21.18 ms | 0.61 ms |
| 10,000 件の一括返信保存 | 451 ms | 263 ms |
| 再起動時の読み込み | 296 ms | 94 ms |
| 読み込み中の最大イベント間隔 | 296 ms | 14 ms |
| 受信中の本部ファイル全置換回数 | 19 回 | 0 回 |
| 受信中の本部記録書き込み量 | 43.53 MB | 4.15 MB |
| 受信＋返信＋再起動の本部記録書き込み量 | 146.37 MB | 24.82 MB |
| 終了時の本部記録ファイル | 5.75 MB | 5.95 MB |

保存の書き込み量は約 83% 減った。最初の一覧作成では再利用用の状態を作るため、この計測では時間が増えた。受信全体も大幅には短縮していない。主な効果は繰り返しの集計、返信保存、再起動中の応答と書き込み量にある。

1,000 件では、繰り返し集計の中央値が 1.45 → 0.10 ms、読み込みが 93 → 65 ms。一括返信は 29 → 31 ms とほぼ同程度だった。

全項目の生データ: [変更前 JSON](measurements/2026-11-13-inbox-before.json)、[変更後 JSON](measurements/2026-11-13-inbox-after.json)。実行ごとに OS の負荷・JIT・キャッシュ・GC の影響で時間と RSS は変動する。これらの 1 回ずつの計測値を端末共通の性能基準にはしない。

## 4. 1 万件への返信で残る制約

本部の保存上限 10,000 件と、中継の保存上限 3,000 件は別のもの。今回の計測では、10,000 件の返信記録はすべて復元できたが、終了時点で **7,116 件の返信が中継用の保存枠から外れ、準備待ち** になった。返信が記録された件数を、そのまま相手へ届いた件数と扱わない。

準備待ちは一覧の「まだ 返事を していない」から再試行できる。ただし、一括再試行だけでは中継用の枠を入れ替え続ける可能性があり、全件への到達を保証しない。全返信を順に運ぶためには、保存確認に応じて未送信返信を補充する仕組みを別途設計する必要がある。

スマートフォンは今回の実行環境に接続されていない。iPhone / Android 実機の BLE、画面オフ、電池消費、端末のディスク不足は [総合テスト](10_test_spec.md#総合テスト) で引き続き確認する。

## 5. 再実行

通常の確認:

```sh
flutter analyze
flutter test
```

今回の最終結果は静的解析の指摘なし、通常テスト **413 件成功**。下記の実ファイル計測 **2 ケース** も成功した。スマートフォン実機での試験を実施済みとして数えてはいない。

1,000 件・10,000 件の実ファイル計測:

```sh
flutter test --concurrency=1 --reporter expanded tool/benchmarks/report_capacity_test.dart
```

件数を変える場合:

```sh
flutter test --concurrency=1 --reporter expanded \
  --dart-define=SANO_BENCH_COUNTS=10000 \
  tool/benchmarks/report_capacity_test.dart
```

`SANO_BENCH` で始まる行が JSON の結果。一時ファイルは終了時に削除する。時間の上限でテストを合否判定せず、記録数、返信状態、再起動後の復元、10,001 件目の拒否を検証する。

- [`report_view_performance_test.dart`](../test/mesh/report_view_performance_test.dart): 本文解析の再利用、権限・期限・取消・時計変更、一括返信中のイベント処理。
